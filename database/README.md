# LedgerGuard MongoDB / Mongoose starter — Revision 3

Updated 22 November 2026 from the backend team's Revision 2 review. This is a reviewable database starter and integration-test suite, not a production certification. Atlas-backed tests must pass in the team's isolated test environment before the contract is frozen.

## Revision 3 changelog

- Corrected the Zenith sample usage cost: `275 / 100` compute units × `10` minor currency units per compute unit = `27.5` minor units, rounded half-up to `28` minor units. The seed now stores `totalCostMinor: 28`.
- Added `PricingPlan.version` (defaults to `1`) and a unique compound index on `{ planCode, version }` so each plan version is unique within a tenant database.
- Kept the existing half-open pricing period convention `[effectiveFrom, effectiveTo)`. Overlap validation now runs for document validation and supported `updateOne`, `findOneAndUpdate`, and `replaceOne` operations. `updateMany` is rejected to avoid bypassing per-document validation.
- Reworked tenant connection creation so the in-flight connection promise is inserted in the cache synchronously. Concurrent requests for the same tenant share one connection attempt/pool. Failed or disconnected connections are evicted for retry.
- Added a request-hash comparison helper and Node.js integration tests for tenant isolation, concurrent connection reuse, idempotency-key uniqueness/request mismatch, pricing version/period rules, and transaction rollback.

## Architecture

- `platform_db.organizations` is the central tenant registry.
- Each organization has a separate database (examples: `tenant_acme_db`, `tenant_zenith_db`).
- Each tenant DB contains `users`, `billingTransactions`, `ledgerEntries`, `usageRecords`, and `pricingPlans`.
- The registry stores the tenant `databaseName`; credentials stay in environment variables or a secrets manager.

## Setup and seed

Requires Node.js 20+ and MongoDB Atlas configured as a replica set or supported sharded cluster. A standalone MongoDB server cannot run multi-document transactions.

```bash
npm install
cp .env.example .env
# Set MONGODB_URI in .env
npm run seed
```

The seed script creates two sample tenants:
- `org_acme_001` -> `tenant_acme_db`
- `org_zenith_002` -> `tenant_zenith_db`

Seed password hashes are placeholders. They are not usable login credentials. Replace them with hashes generated by the backend's chosen password-hashing library before authentication testing. Run the seed only against a development database.

## Schema contract

### BillingTransaction
- `transactionId`: unique transaction identifier.
- `organizationId`: tenant identifier.
- `amountMinor`: safe integer in currency minor units (₹1,299.00 = 129900 paise).
- `currency`: 3-letter currency code.
- `status`: `pending`, `success`, `failed`, or `reversed`.
- `idempotencyKey`: unique within this tenant database.
- `requestHash`: SHA-256 hex digest (64 characters) of a canonicalized request payload. Backend must define the canonical fields and reject a reused key with a different hash.
- `failureReason`: optional bounded diagnostic text; do not store secrets or sensitive payment data.
- `reversedAt`: timestamp set when reversed; otherwise null.
- `idempotency`: status, replayable response, and completion timestamp.

### LedgerEntry and reversals
Normal entries have `reversalOf`, `reversalOfJournalId`, `reversalOfTransactionRef`, and `reversalReason` set to null. A compensating entry points to the original ledger row and original journal/transaction. Reversals are new entries; never delete or mutate original entries. The backend service must ensure the reversal correctly compensates the original journal.

### UsageRecord — scaled integer quantities
- `quantityScaled`: non-negative safe integer.
- `quantityScale`: positive safe integer.
- Actual quantity = `quantityScaled / quantityScale`.
- `unitPriceMinor` and `totalCostMinor` are integer minor-currency units.

Example: 2.75 units at 10 minor units per unit gives 27.5 minor units. This starter uses half-up rounding for the sample and stores 28. The backend must confirm and consistently apply its rounding rule for all billing calculations.

### PricingPlan versions and effective periods
- `version` is a positive safe integer, default `1` for compatibility with existing plan documents.
- Unique index `{ planCode: 1, version: 1 }` prevents duplicate versions for a plan code within one tenant DB. Before creating this index on an existing database, backfill `version` and resolve any duplicate `(planCode, version)` pairs; the default of `1` does not automatically distinguish historical versions.
- Periods are half-open: `[effectiveFrom, effectiveTo)`; null `effectiveTo` means no end date.
- For a given `planCode` and `metricType`, periods must not overlap.
- Overlap checks run on document validation and `save`-style document writes, plus `updateOne`, `findOneAndUpdate`, and `replaceOne` query updates. Query updates support direct assignments and `$set`, `$setOnInsert`, `$unset`, and `$inc`. Aggregation-pipeline updates and `updateMany` are deliberately rejected for PricingPlan; use a validated single-document update instead.

**Concurrency caveat:** Mongoose overlap validation is an application-level guard. Two independent writers can still race between checking and writing. The backend must serialize pricing-plan changes (for example, a tenant-scoped lock or transaction with an agreed conflict strategy) and handle duplicate/overlap errors. A normal unique index cannot enforce arbitrary date-range non-overlap.

## Tenant connections

`getTenantConnection(verifiedOrganizationId)` looks up an active tenant mapping in `platform_db` and caches/reuses tenant connections. The promise is cached before the first await so simultaneous requests share the same in-flight connection attempt. Failed/disconnected connections are evicted and a later request can retry.

Call this function only after JWT signature, expiry, issuer, and audience checks have succeeded. JWT verification and Redis locking are owned by the backend team. Never accept a database name from a client or trust an unverified JWT claim.

## Idempotency and atomic billing responsibilities

`src/idempotency.js` exports `assertMatchingRequestHash(existingRecord, incomingRequestHash)`. It returns true for a new request or matching retry and throws a 409 mismatch error for a reused key with a different hash. This helper does not claim the idempotency key, persist records, or replace a unique index/transaction; the backend service must do those atomically.

For each tenant billing operation, use one tenant connection and one MongoDB session for the billing transaction and all ledger writes. The backend service must:
1. Claim/check the idempotency key and compare canonical `requestHash` values.
2. Create/update the billing transaction.
3. Insert balanced debit and credit ledger rows under one `journalId`.
4. Verify debit total equals credit total for each journal and currency.
5. On reversal, insert compensating entries linked to original entries and set `reversedAt`.
6. Store the replayable idempotency response and commit all changes together.

A journal's cross-document balance cannot be guaranteed by a document validator; enforce it in the billing service inside a MongoDB transaction. A session cannot span separate tenant database connections.

## Automated tests

Fast local/unit checks (do not require MongoDB):

```bash
npm test
```

Atlas integration tests are skipped unless both `MONGODB_URI` and `LEDGERGUARD_TEST_PLATFORM_DB_NAME` are set. Use a dedicated disposable test cluster/database; never point these tests at production. Example:

```bash
export MONGODB_URI='mongodb+srv://<test-user>:<password>@<test-cluster>/?retryWrites=true&w=majority'
export LEDGERGUARD_TEST_PLATFORM_DB_NAME='ledgerguard_test_platform'
npm run test:integration
```

The integration suite creates two temporary tenant databases with unique names, checks tenant isolation, concurrent connection reuse, idempotency uniqueness and request-hash mismatch behavior, pricing version/period validation, and transaction rollback. It drops its test platform and tenant databases on completion. Ensure the Atlas test user has permissions to create/drop databases and run transactions. If the process is interrupted, manually remove databases with the `ledgerguard_test_` / `lg_test_` prefixes created by that run.

## Index and operational notes

- Platform unique indexes: `organizationId` and `databaseName`.
- Tenant unique indexes: user `email`, transaction `transactionId`, transaction `idempotencyKey`, usage `eventId`, and pricing `{ planCode, version }`.
- Create indexes in every tenant DB before serving traffic; verify existing data has no duplicates before building unique indexes.
- The pricing overlap check is not a substitute for serialized pricing writes. Do not bypass model middleware with raw collection writes or `bulkWrite` for PricingPlan.
- `quantityScale` must be consistent for a metric/unit and agreed in the API contract.
